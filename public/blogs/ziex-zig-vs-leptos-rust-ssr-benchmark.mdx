Ziex is a full-stack web framework for Zig: JSX-style markup right inside Zig code. It pitches itself as a fast server-rendering framework, fast enough to go head-to-head with the big Rust frameworks.

I love Rust, so a Zig framework going after Leptos at server rendering was worth checking. One machine, two containers, same load generator, same page.

**Result:** on my machine, Leptos won, and comfortably.

- **Throughput:** Leptos **~157k req/s**, Ziex **~88k req/s**. Leptos ~79% ahead.
- **Median latency (p50):** Leptos **0.24 ms**, Ziex **0.44 ms**.
- **Tail (p99):** close, **1.95 ms** vs **2.50 ms**.
- **Errors:** zero on both, millions of requests each.

Code, Dockerfiles, and the harness: [github.com/zahinafsar/ziex_zig-vs-leptos_rust](https://github.com/zahinafsar/ziex_zig-vs-leptos_rust)

## The workload

Both render the same page: a `<main>` with 50 rows, each `<div>SSR {v}-{i}</div>`, built by a server-side loop and generated fresh every request. No caching, no precomputed string. This is the same list Ziex uses in its own benchmark repo, so neither side got an easier page.

Ziex builds it with a template `for` loop:

```zig
pub fn Page(ctx: zx.PageContext) zx.Component {
    const arr: [50]u32 = @splat(1);

    return (
        <main @allocator={ctx.arena}>
            {for (arr, 0..) |v, i| (
                <div>SSR {v}-{i}</div>
            )}
        </main>
    );
}

const zx = @import("zx");
```

Leptos builds the same rows through a component, served by actix-web:

```rust
#[component]
fn SsrPage() -> impl IntoView {
    let items: Vec<u32> = (0..50).map(|_| 1).collect();

    view! {
        <main>
            {items
                .into_iter()
                .enumerate()
                .map(|(i, v)| view! { <div>"SSR " {v} "-" {i}</div> })
                .collect_view()}
        </main>
    }
}
```

Both live behind `docker compose`. Load comes from a third container running `oha` on the same bridge network, hitting each server by its internal name so neither pays for host port forwarding:

```bash
oha -z 20s -c 50 --no-tui --output-format json http://ziex:3000/
oha -z 20s -c 50 --no-tui --output-format json http://leptos:3000/
```

Same box, same network, same generator, or it does not count.

## The one unfair bit, and it favors Ziex

This Ziex dev build always compiles a client WASM bundle and injects a preload `<link>` plus a `<script>` into the `<head>`, even with `config.csr = false`. There is no flag in this version to turn it off. My Leptos app ships pure SSR with no client bundle. So Ziex's response carries a couple of extra tags Leptos's does not. `oha` never fetches those sub-resources, so they cost bytes, not render time. The asymmetry that exists works against Leptos, and Leptos still won.

## Read it with care

This is my laptop, and Ziex is `0.1.0-dev`. Actix and Tokio have been tuned for exactly this kind of load for years, and Leptos rides on top of that. Ziex's `serve` path is not final, and the project says so. A pre-1.0 Zig framework holding a mature Rust stack to under 2x on throughput and staying level at the tail is a good showing, not an embarrassment.

If you see Ziex ahead somewhere else, look at the setup. A `cargo-leptos` hydration build does more work per request than my server-only render, and hardware and harness swing these numbers hard. Benchmarks are arguments about setup, and this one is mine.

## So, should you use Ziex?

Nobody embarrassed themselves. Both did millions of requests, zero errors, sub-millisecond medians, on a page that actually renders data.

Ziex is genuinely fun: writing HTML inside Zig with real control flow, compiling to one static binary, is a lovely place to work. But it is early, and here Leptos was faster across the board. If you need production SSR today, Leptos is further along and, on my hardware, quietly ahead. If you want to bet on where Zig web frameworks are heading, Ziex is worth watching, just know you are on the `dev` releases.
